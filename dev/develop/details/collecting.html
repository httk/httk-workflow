Collecting results¶

Collecting is the read-only counterpart of running work. The low-level job_records() iterator reads each stopped job into a JobRecord: where its files are, what produced them and what happened on the way. The framework-level collect() passes each record to its registered workflow’s collector and yields a CollectedJob with role-keyed outputs, provenance, products and any unfulfilled roles.

Collected jobs¶

Degraded and run-only jobs¶

A job that cannot be collected at all yields a degraded CollectedJob. missing_collector explains why, outputs is empty and unfulfilled names every declared output role, so it cannot be mistaken for a complete collection that declares no outputs.

A workflow with nothing to collect, whose registered provider has no collector and declares no outputs, is not degraded. Its CollectedJob is complete, with run_only set, no outputs and the job’s run as its only product, its staged files recorded as its inputs (see Staged inputs record the exact file). Orchestrating workflows that only spawn or call others, and the small steps they call, are typically like this.

Every CollectedJob also carries child_runs: one (label, run source id) pair per child the job spawned or called, read from the published children of its state.json.

When an output role is a single file-valued result, its run edge points to a standard files entry (type = "files"). File lists remain values within their role record.

A files entry is identified by its content: its media type (application/octet-stream unless known), its format (the httk₂ reader tag, such as vasp-poscar, when one is set) and the SHA-256 digest of its bytes. The same bytes at many locations are one entry, which keeps the URL, name and size it was first stored with. A FileRecord therefore needs a sha256 of 64 lowercase hex digits: a hook building one (or returning a {"entry": {"type": "files", ...}} response) must compute it, for example with httk.core.digests.sha256_file. The framework computes it, and sets format from the file name, for a {"file": ...} response and for staged inputs.

A files entry of a workspace job whose URL is a relative path (neither absolute nor scheme://) gets the fixed URL data/<workspace name>/<url>. The workspace name is the registered name whose path is the workspace root, or the root directory’s name. A hook that builds a FileRecord with the bare workspace-relative path is prefixed the same way. Only a normalized relative path is prefixed; one with an empty, . or .. segment, or one that already starts with the prefix, is left as it is with a warning naming the job and the role. The URL is metadata, not part of a file entry’s identity (its media type, format and SHA-256), so the same workspace collected under another registered name yields the same file entries, and a store keeps the first non-null URL it was given. Where the files are served from is a serving-time choice instead: httk serve optimade serve STORE --data-path DIR (or NAME=DIR) serves the bytes, --data-url URL points at an external file server (httk-serve). Recognized calculation trees keep their URLs as their collectors give them.

Inputs¶

A workspace job’s CollectedJob.inputs holds the entries the job consumed, and each becomes a run input edge before product_of curations resolve, so a curation naming an input role links to it instead of being reported in products_unlinked. --into stores the inputs like outputs, and the run’s input edges name their stored ids. Inputs come from two places:

  • The collect hook may hand them over (see Executable hooks for the stream form): a Python hook returns httk.workflow.hookapi.Collected(outputs, inputs) instead of a mapping of output roles. This is how an input given through a port, such as a jobflow structure staged as a pymatgen JSON file, names the entry it consumed.

  • The framework records every file staged into the job, as described under Staged inputs record the exact file.

A hook reads the files a job wrote with record.read_file(relative), which returns the bytes of a file below the job’s payload (for example record.read_file("data/jobflow/jobflow-outputs.json")) the way the framework reads job-writable content: it follows no symlink, refuses a FIFO or other special file without blocking, and refuses a file larger than limit (default 64 MiB). An absent, unsafe or oversized file is a ValueError.

An input role a hook hands over that the job’s workflow declaration does not list is a collector error that degrades the job. The framework’s own staged inputs are labelled from the job’s job.json, which named them, and are not checked against the declaration.

Staged inputs record the exact file¶

Inputs are staged into the job verbatim, and what the workflow does with them afterwards is its own business, so the store records exactly the files the workflow received. Two kinds of staged file are recorded:

  • Every declared input (declared.inputs of job.json) with a destination, typed or not, labelled by its role. The file is where submission staged it: a bare name such as POSCAR at <payload>/files/POSCAR, a name with a directory such as inputs/POSCAR at <payload>/inputs/POSCAR. When the collect hook hands over the role’s entry (or the observed provenance already has an edge for it), that entry keeps the role and the staged file is still recorded, labelled by its payload-relative path. An input without a destination (a port, such as a jobflow input handed over from a parent job) is a value, not a staged file, and only a hook can record it.

  • Every file job new --file/--files staged (also with --from-command, the files argument of httk.workflow.new_job, and the files of a child that Attempt.call creates), listed in the staged_files member of job.json and labelled by its payload-relative path, such as files/INCAR. A listed file that is also a declared input’s destination is recorded once, as that input. A job created before staged_files existed records none of these.

When job new stages a file, --file/--files and declared-input destinations alike (copied, or written with httk.core.save for a loaded object), it records the file’s size and SHA-256 in staged_files. Collect then records each input exactly as staged:

  • When the job has a usable seal (.httk-job/seal.json, written when the job succeeds), a file the seal records with the staging digest is as staged and is recorded without being read again. A file the seal records with another digest, or not at all, was mutated or deleted during the job. The seal is trusted like job.json, so it is usable, signed or not, when its body matches its recorded digest; a seal whose body was tampered with, or a signed one whose signature does not verify, is no seal (with an info message).

  • Without a usable seal, the file is read as below: a missing file, or one with another digest, was mutated or deleted during the job.

  • A runner-prepared payload whose staged_files lists a path without a digest is read and recorded as it is; a changed file cannot be detected there.

A mutated or deleted input is recorded as lost: a files entry with no URL (url is null), the staged name and the staging size and digest, with an info message naming the role or path. The run’s input edge names it, and a structures input that is lost is recorded as this file only, not loaded. A lost entry is served with an ni:///sha-256;... URI in place of its URL, and the store’s fsck counts it as lost instead of checking a location. The mutated bytes are not recorded as an input: they are recorded only when the workflow declares them as an output. Because file entries are identified by content, a later job that stages the same bytes and leaves them alone fills in the lost entry’s location when it is stored.

A staged input file in the payload is the job’s record of that input, so a runner works on copies in its working directory (as stage_input makes them) and never rewrites a payload input. Staging digests are taken at job new, after its instantiate hooks, so a runner that rewrites a payload input at run start has that input recorded as lost.

Mutation detection is authoritative only with a signed seal from a trusted manager. In an unconfined run a job can rewrite its own unsigned seal, so the comparison then relies on the job not tampering with its own state, as job.json does.

Every such file that is a regular file, of any size, type or name (POTCAR included), becomes at least a files entry: its URL (data/<workspace name>/<workspace-relative path>), name, size, SHA-256 digest and, when a registered reader matches the name, its format (for example vasp-poscar). The digest is streamed from one read without a size bound, the way record.read_file (above) reads job-writable content, so a symlink or a special file is skipped with a warning, never followed. A compressed file (POSCAR.gz) is hashed as stored, not decompressed, and its format is that of the uncompressed name. File entries are identified by content, so the same bytes staged by many jobs are one entry, which keeps the URL it was first stored with. The bytes stay in the workspace; the store holds the URL and the digest. A declared input that is not staged is skipped with a warning, or an info message when it is not required; a staged file that is gone is recorded as lost (above). A job collected into a store by an earlier httk₂ that recorded fewer inputs gains these edges on its next --into sweep, so its run is stored again as a new revision (revised in the report); this is expected, not a sign of changed results.

The run’s input edge names that files entry, except for a structure httk₂ can read:

  • A structures input that is not compressed and at most 64 MiB (READ_FILE_LIMIT) is also loaded, from exactly the bytes that were hashed, and becomes two entries from that one reading, its numbers exactly as written (a CIF site on a declared Wyckoff position takes that position’s exact coordinates). The main entry is the structure as httk₂ reads it (any loaded structure wrapped as a UnitcellStructureView, which needs httk-atomistic), so equal structures share it. Its alternative of kind file_<hex> (the first 16 hex digits of the staged file entry’s content id) is the same reading with the staged file as its source_file. Different files of one structure are different alternatives of the same main; the same bytes are one. Re-collecting a job into a store collected before numbers were read as written by default gives its structure a new main entry, with the file’s alternative under it, and revises the job’s run to name it, leaving the earlier entries in place; rebuild such stores (collect into a new file) instead. The run’s input edge, and any product link drawn from that role, names the alternative as <main id>~file_<hex>.

  • A structures input that is compressed, larger than 64 MiB or not loadable as a structure is recorded as its files entry only, with a warning naming the reason.

  • An input of any other declared entry type (a trajectory, for example) is recorded as its files entry, with an info message; collect does not load it.

The digest tells whether a copy is still the file the job received.

Files moved to another job¶

A file moved out of a succeeded job into a new one (job new --input-move-from-job, see Sealing jobs, workspaces, and projects) is gone from its first job, and a valid release record beside that job’s seal says where it went. The framework records such a file by its release record instead of failing on it:

  • A {"file": ...} response of an executable collector (and a CWL output file, or a published data file) that names the missing file becomes a files entry at the new location, data/<workspace name>/<the receiving job's payload>/<path>, with the size and digest the seal records, and a warning naming the receiving job. The run’s output edge names that entry.

  • A staged input that was moved on is recorded the same way, with an info message, not as lost.

Only a stable location is recorded. While the receiving job has not succeeded it still moves between state directories, so the entry has no URL yet; the receiving job’s own collect records the location, and a store keeps the first non-null URL. The URL settles once the receiving job has succeeded. A release record whose file is present (a move that never happened) changes nothing.

File entries are identified by content, so the receiving job’s own input is the same entry. A package collector that reads an output file itself (with record.payload / ...), rather than returning {"file": ...}, cannot read a moved file, so its job collects as degraded.

A crash between the move and the new job’s submission keeps the file in a scratch directory under .httk-workspace/tmp/, and a warning names it. The operator then moves the file back to its job by hand.

If the first job was stored before the move, its stored files row still holds the old URL, which a later save would keep. When the job is collected --into the store again, each released file is re-pointed to its new URL (or to no URL while the receiving job has not succeeded), but only while the row still holds the old one (a compare-and-swap); a row someone else re-pointed is left as it is, with an info message.

Runs and product curation¶

The job-embedded declaration governs the Run (the job’s immutable facts). The Run carries the executing system’s job identity in source_id; httk-store mints its store-owned immutable_id.

Product curation (product_of on an output role) comes from the live registered provider’s manifest, so today’s curation applies. Under the job-pinned fallback it comes from the job’s verified pinned manifest, keeping its historical curation. With neither reachable, no products are emitted.

A data-record output whose role is product_of another role gets that source as a product_of edge on the record itself. The edge is a StrongLink with the same (label, entry_type, entry_id) scheme as run edges, so it is record content and searchable as record.links.product_of == structure. Every curation is also emitted as a ProductLink.

Introducing product_of as record content changed every DataRecord content id and the record layout. A store created before that change and holding data records must be rebuilt (--into a new file), not reopened.

Records as the layering boundary¶

JobRecord is the layering boundary of httk₂. httk-workflow has no database dependency: it produces records and httk-store consumes them. A consumer reads results like this, and nothing in httk-workflow knows what store or load_vasp are:

from httk.workflow import Workspace, job_records

workspace = Workspace("workflow-workspace")
for record in job_records(workspace):
    store.save(load_vasp(record))

Every member of a record derives from the job directory alone: the immutable job.json, the owner-written state.json and the owner run log logs/runlog.jsonl. A record never says anything the workspace does not. It identifies its job by workspace_id and job_id; a job directory moves with every state change, so payload_path is only where the job was when it was read.

What a record guarantees¶

The executed code is pinned¶

A record carries the immutable job digest and, in runner_provenance, the installed workflow the job ran: its id and the SHA-256 of its installed package tree, as the manager recorded them at launch (workflow_pin in state.json). A stored result therefore names the software that produced it. For a job that set_workflow switched, collection resolves the provider, the collector and the run’s workflow_definition_uri from that pinned installation rather than from the declared workflow. An unlocked job (see Unlocked jobs) is the exception: it may have run from its own edited copy of the package, so its pin names the digest of that copy and no installed tree.

Unlocked jobs¶

A job in debug mode (httk job unlock, see Restarting and resuming jobs) carries the state.json unlocked marker, and its code, job.json and even its succeeded state may have been changed by hand. Collection therefore does not store it unless told to:

  • collect() yields it degraded, with missing_collector set to job is unlocked (debug mode); pass --force to collect it. As for any degraded job nothing is stored, and the sweep exits nonzero.

  • collect_postprocess (--postprocess) sets CollectedPostprocess.error to the same text, which makes the command exit 1.

  • collect(..., force=True) (httk collect --force) collects it, also with --postprocess. The job’s registered provider’s collector is used as for any job; the collect hook of the runner copy (workflow/ in the job directory) runs, unverified, only with --allow-job-collector, only when no in-process registered provider supplies a collector, and only after the job has run again from the copy (workflow_pin source "copy") with the copy unchanged since that launch. Unlocking a finished job and collecting straight away degrades the job with the job's last attempt did not run from its runner copy; restart it before collecting; the other reasons read runner copy modified since the job ran: ... digest X does not match pinned Y and ... could not be verified. An unlocked job without a copy uses the installed tree as before. With --into, the run is stored with no mark that the job was unlocked: whoever forces the collection takes the responsibility.

  • A job with an embedded workflow (created with job new --embed-workflow, see Workflow packages in detail) is not degraded by its tree: with --allow-job-collector, and only when no registered provider supplies a collector, collection copies workflow/ into a private snapshot in the system temporary directory (removed when the collect window ends; unlocked runner copies are collected the same way), computes the embedded digest of the snapshot, requires it to equal both job.json’s embedded.tree_sha256 and the launch pin (source embedded; an unlocked embedded-workflow job needs source copy or embedded and the pin digest), loads Python hooks as modules private to the snapshot (identical trees of two jobs never share a module) and runs executable collectors with the snapshot as working directory. A registered provider with the same short name is never used for an embedded-workflow job. Otherwise the job degrades with the job's last attempt did not run from its workflow/; restart it before collecting, embedded workflow modified since the job was created: the last launch pinned <X>, job.json <Y>, ... digest <X> does not match pinned <Y> or ... <path> could not be verified: <error>. An unlocked embedded-workflow job whose launch pinned no digest is refused with the job's workflow/ could not be digested at launch (its launch pinned no digest); fix it and restart before collecting. Unlocked copies keep their existing texts. Only that job degrades. Nothing is ever executed from the payload itself, and without --allow-job-collector a payload never causes code to run at collection. CollectedJob.workflow_id is the embedded id, and the definition URI is embedded.source when it is a commit-pinned git URI, else None.

  • Every per-job summary line of an unlocked job, degraded or forced, and the store report carry "unlocked": true, and JobRecord.job["unlocked"] carries the marker.

  • --raw and campaign collection are readouts and do not check the marker.

Damage is reported¶

A job whose run log, state.json or observed declarations are damaged is still collected with whatever remains readable, and provenance.gaps is set to true, so a result does not vanish because part of its history was lost. Only a job whose job.json cannot be read is skipped, with a module-logger message, because a record stands for the validated job behind a result.

Collection scales by iteration¶

job_records is a lazy iterator over one listing of the requested state directories, and each record reads only its own job’s job.json, state.json and run log. A job that moves between listing and reading is skipped like an unreadable one. Scale benchmarks gives a measured local reference point. Partition larger campaigns across workspaces and collect them one partition at a time, not as one in-memory result array.

payload_path, workdir_path and data_path are workspace-relative, so a stored record survives moving the workspace. The properties record.payload, record.workdir and record.data resolve them to absolute Path objects against the record’s workspace.

Parameters and result files¶

A collect hook reads parameters and finds result files through the record:

  • record.parameter(name, default) returns one member of the job’s parameters. Without a default, a missing name raises KeyError, like Attempt.parameter.

  • record.result_file(name, data_prefix=..., published=...) returns the existing file: below the committed data for a job that has a data/ directory (at published, default name, below data_prefix), otherwise in the persistent workdir. A compressed copy (OUTCAR.gz) is found too. A missing file raises ValueError; a job with committed data never falls back to the workdir.

  • record.read_file(relative, limit=...) returns the bytes of one file below the job’s payload, read as job-writable content is read: no symlink is followed, a FIFO or special file is refused without blocking, and a file over limit (default 64 MiB) is refused; each of those, and an absent file, raises ValueError (see Inputs).

from httk.codes.vasp.collect import read_total_energy


def collect(record):
    prefix = record.parameter("data_prefix", "vasp") or ""
    return {"total_energy": read_total_energy(record.result_file("OUTCAR", data_prefix=prefix))}

The reading helper comes from the code package, here httk-workflow-vasp.

Provenance, children and declarations¶

The timeline regroups the owner run log: each attempt_started event opens an attempt, and a change of activation opens an activation. Each entry of provenance.activations carries activation_id, activation_ordinal, the step it ran, the reason it started (known for the current activation, from state.json) and its attempts. Each attempt carries attempt_id, ordinal, the owner_id that launched it, the claimed_at, started_at and finished_at timestamps, the outcome_action it published and its failure (the code from the run log; the full failure for the last attempt). The runner’s own evidence log .httk-job/runlog.jsonl is not part of the record; httk job log shows both.

children maps each spawn label to job_id, job_key and kind, the state the parent’s join last observed the child in (null when no join observed it). A campaign thus collects as a tree of named children, each collected in its own right.

declarations reports every declaration name either source knows:

  • declared is the document job.json carried, pinned by the immutable job digest.

  • observed is the runtime-refined document the job wrote below .httk-job/declarations/.

Either is null when its source has nothing. They are not merged, because reconciling them needs the document’s own vocabulary, which is the consumer’s job. An unreadable observed document is reported as null and sets provenance.gaps. job does not repeat the declared documents. See Workflow declarations.

The observed environment declaration is the exact resolved value and source snapshot that drove the run (format httk-workflow-environment-resolution version 2). The provenance declaration becomes a stored httk.core.Run; see Run provenance.

Selecting records¶

records = job_records(
    workspace,
    states=("succeeded", "failed"),
    placement="project/campaign",
)

states defaults to ("succeeded",) and accepts only the states of stopped jobs: succeeded, failed, cancelled and paused; other values are refused by name. placement restricts collection to jobs at or below one placement, as httk job list --placement does.

jobs (--job JOB) selects job trees instead:

records = job_records(workspace, states=("succeeded", "failed"), jobs=["campaign--4f0c"])

Each selector is resolved as httk job show resolves it (a UUID, a job key, a unique prefix, or a path inside the workspace; a path is relative to the current directory), and an unknown or ambiguous selector is a ValueError naming it. The selected jobs and all their descendants, followed through the children of each state.json, are yielded depth-first, parent before its children, each job once. A selected job that has not finished and is not in states (ready, running, waiting, or paused unless paused is requested) is a ValueError naming the job and its state. A finished job outside states, selected or a descendant, is skipped silently as in a sweep, and its descendants are still walked: collecting a failed parent with the default states yields its succeeded children. A child whose directory cannot be found, and a job whose damaged state.json hides its children, are passed to on_skipped (the job itself is still collected, with gaps set). jobs and placement cannot be combined. collect(..., jobs=...) passes the selection through.

steps (--step STEP) keeps only the jobs at one of these steps: the step of the job’s current activation, or the initial step of its job.json before the first. It narrows a sweep and, with jobs, the reported jobs (the tree is still walked). A job left out for its step is not passed to on_skipped and is not counted as skipped. collect, campaign_collect and collect_postprocess take steps too.

From the command line¶

httk collect --workspace WORKSPACE
httk collect --workspace WORKSPACE --state succeeded --state failed
httk collect --workspace WORKSPACE --placement project/campaign --raw
httk collect --workspace WORKSPACE --force      # also collect unlocked jobs

httk collect also takes a PATH. A workspace root or a registered workspace name collects that workspace; any other directory is walked as a tree of finished calculations (see Recognized calculations below).

See Project and workflow command line in detail.

Summary line and exit codes¶

Every collect invocation ends with one JSONL summary line:

{"format":"httk-workflow-collect-summary","format_version":2,
 "collected":N,"degraded":N,"unfulfilled_roles":N,
 "storage_errors":N,"skipped_unreadable":N}

A calculation-tree sweep adds "unclaimed":N, the directories a collector declined. A sweep with --into adds "revised":N, the jobs whose stored entries gained a revision.

  • collected: jobs collected without degradation.

  • degraded: degraded jobs.

  • unfulfilled_roles: declared roles left unfulfilled, summed over all jobs.

  • storage_errors: jobs an --into store could not persist.

  • skipped_unreadable: jobs dropped because their job.json could not be read. They never appear as records; this count is the only place they surface.

The command exits 0 only when degraded, storage_errors and skipped_unreadable are all zero. Unfulfilled roles alone do not fail the sweep; a partially fulfilled job is a normal result. As a gate, a nonzero exit means a job could not be collected, stored or read, and the counts say which.

Per-job triage¶

Each summary line carries its own triage fields:

  • missing_collector explains a degradation; for an unlocked job it says to pass --force.

  • unlocked is true on every line of a job that carries the debug-mode marker.

  • products_unlinked lists product_of links skipped because the output was produced but its curated source edge is absent from the observed provenance, as "<role> -> <source> (source edge absent in observed provenance)". A product whose own output role went unfulfilled is reported only through unfulfilled.

  • collector_exit_status reports an executable collector that answered every record but still exited nonzero.

Storing results with --into¶

With --into PATH --id-base BASE, each collected job’s entries, run and product links are saved into a file-backed SQLite store, and its report gains "stored": {...}.

Degraded and failed jobs¶

A degraded job stores nothing: its report carries "stored": null, "skipped": "degraded" and no empty Run is written. An unlocked job is degraded this way unless collected with --force (see Unlocked jobs). A job whose entries cannot be stored keeps a "storage_error" and fails the exit code.

Run-only jobs and child runs¶

A run_only job stores its run by default, so an orchestrating parent and every job it spawned or called each leave one runs entry (served as _httk_runs) naming their own workflow declaration and, for a commit-pinned git workflow, its definition. --no-bare-runs opts out, and such jobs then report "stored": null, "skipped": "run-only". Their report lines carry "run_only": true, and a job that spawned children lists them as "children": [{"label", "run_source_id"}].

A parent’s stored run gains one has_artifact edge of type runs to the run of each child it spawned or called, including detached children (detaching changes where a child may move, not who created it). The edge is labelled by the spawn label, or by the child’s run source id if that label is taken on the artifact side. Children are stored before parents so their runs exist. A child collected but not stored in this sweep (degraded or skipped) is left out, as is one never collected; one stored by an earlier sweep is linked.

Revisions¶

Each job has one run entry. A changed run on re-collection, such as a parent whose children were collected since, is stored as a revision of the same entry (same entry id, one lineage); unchanged runs deduplicate. With an id ledger, a job’s record whose content changed since the last sweep likewise keeps its ledger id and gains a revision. The report line then carries "revised": true.

Entry ids and the id ledger¶

--id-base is required with --into and names the dot-separated namespace for minted entry ids. --id-series selects the campaign series and defaults to 1.

By default a sealed id ledger allocates these ids so they stay stable across rebuilds; see Stable ids. It lives beside the store at <into>.ids.sqlite (relocate it with --id-ledger PATH), is created and signed on first use, and is announced prominently because it should be kept and committed with the store.

--no-id-ledger opts out, and a sweep without a resolvable workspace signing key has no ledger. Either way the store mints ids that are not stable across rebuilds, with one warning.

An output that already carries an assigned public id is not renumbered. Content the store deduplicates onto one row is recorded as one id, with the other keys aliased to it. A job whose identity is not stable (a v1 tree with no manifest) is store-minted with a warning instead of pinned to a stale key.

Resolving references¶

Before persistence, edges to output records that have no store id yet use those records’ content ids. --into then stores in two passes:

  1. It commits all job outputs while building one sweep-wide map from content id to entry id.

  2. It rewrites and commits the runs and product links.

A reference not produced in the sweep first keeps an already stored public id, then resolves against the destination store by content id. An unknown 64-hex content id makes that job a storage error: its outputs stay saved, but its run and products are not written. Other loose external references are kept unchanged.

Re-collecting into a store¶

Re-collection is stateless and safe: collect --into reads the workspace afresh and writes what it finds. Re-storing a stored job deduplicates on its stable entry, run and product ids, so a repeated collect changes nothing.

A store built under a different entry-family layout is not migrated in place; point --into at a new store file when the layout changes. Reusing a store whose entry-type layout does not match the sweep fails fast. The error names the store path, the entry types the sweep needs and the layout difference, and ends with Collect into a new store file.

Literature references¶

A job whose workflow package declares [workflow.references.<LABEL>] (see Workflow packages in detail) lists the labels as "references" in its report. --into stores each reference as an OPTIMADE references entry and links it from every stored output entry and from the job’s run, which then serve it as relationships.references; staged inputs do not cite. The stored ids appear as "stored": {"references": [...]}. References are deduplicated by content, so jobs of one package share one entry, and re-collecting adds no duplicate links. Links are never retracted: to drop a reference removed from the manifest, rebuild the store. An output whose record type declares no references weak link (a third-party record) is stored uncited, with a warning and its role listed in "stored": {"references_uncited": [...]}. Collecting a package with references into a store built without them refuses with an additive-layout message; rerun with --upgrade to add the references family.

Postprocess output as runs¶

httk collect WS --postprocess NAME stores what the curated script NAME (outputs) wrote for each job. Order matters: collect the jobs first, so each job’s run is in the store, then collect with --postprocess; the script itself may run before or after the job collect. Without --into it previews. Collection reads each job’s .httk-postprocess.json receipt, so it needs no installed provider.

Per job and script one run is stored with source_id <workspace_id>:<job_id>:postprocess:<script>. Its inputs are all of the job run’s outputs plus an input edge job to the job’s run; its outputs are files entries labelled by their output-relative path, with urls data/<workspace name>/postprocess/<placement>/<job_key>/<script>/<path>. The run id is ledger-keyed; the files are not: they are store-minted and content-deduplicated, so identical bytes share one file entry and its first stored url. Recollecting unchanged output stores nothing; changed output revises the same run under the same id. Output equal to an earlier revision’s content (A, then B, then A again) cannot be made current again and is reported as an error: “postprocess output equals an earlier revision (<immutable id>) of run <id>; the store cannot make an earlier revision current again”.

The first postprocess collect into a store whose layout has no files family (no job stored a file yet) needs --upgrade; a store that declares files with zero rows needs none (the upgrade is an additive layout upgrade; back the store up first). The command ends with one httk-workflow-postprocess-collect-summary line and exits 1 on any error or unreadable job.json (an unlocked job is an error, see Unlocked jobs); jobs with no receipt, a failed script, no declared outputs or no matching files are skipped (exit 0). httk serve optimade serve STORE serves the runs and files, and the job’s run shows the postprocess run through the reverse _httk_is_input relationship.

Accepted limits:

  • Only the workspace’s own postprocess/ directory is collected, not a postprocess.directory elsewhere or --output-dir runs.

  • Bytes are not copied and the output directory is reused. A rerun changes the bytes behind already-stored urls until you recollect (served checksums and fsck reveal it), and stale files from an earlier run still match globs.

  • A moved job’s earlier postprocess output is orphaned.

  • Concurrent runs of one script on one job are last-writer-wins.

Workflow collect hooks¶

collect() is the workflow-owned collection layer, and the collect hook a workflow package provides is the workflow-owned substep of collecting. For each record, collect():

  1. resolves the record’s workflow id through workflow_provider();

  2. calls that provider’s collector, a callable or a lazy module:function;

  3. validates role names against the declared outputs in the job’s embedded workflow declaration;

  4. assembles the Run, the data records’ product_of edges and the ProductLink values.

Product curation comes from the provider manifest, as described under Runs and product curation; the embedded declaration supplies only the immutable Run facts. Old jobs without that declaration use the currently registered provider declaration, so their roles are interpreted live, not historically.

Missing collectors¶

  • A workflow without a provider, or whose provider declares outputs but has no collector, yields a degraded CollectedJob with missing_collector set.

  • A provider with neither a collector nor outputs yields a run_only job (see above).

  • A job whose provider is not registered on the collecting machine stays degraded, not run-only, because a collector may exist for it elsewhere.

  • With --allow-job-collector, a job is decided by its verified installed package instead, so an unregistered package with nothing to collect is run_only too.

  • A job of a runner file of your own runs an ad hoc installed package whose generated manifest declares no collector and no outputs, so it is degraded without --allow-job-collector and run_only with it.

--allow-job-collector lets collection load the collect hook of the job’s installed workflow package in the workspace, after checking that its tree digest still matches the job’s runner_provenance (a workflow reinstalled or modified since the job ran is refused; a reinstall’s refusal names both digests and the remedies: reinstalling the tree it ran with, or rerunning the job on the installed tree with httk job request restart (continue --tree when it failed waiting on failed children), a succeeded job by deleting it and creating it again); refusals degrade only that job. See Workflow packages in detail for the trust tiers and package hook contract.

Executable hooks¶

An executable [workflow.collect] member runs once per matching collection window from its package tree. Under the job-pinned fallback that tree is the job’s installed package, digest-checked against the pin. A registered-directory provider is the explicit-consent exception that runs from current source.

The first stdin line is {"format":"httk-workflow-collect-stream","format_version":2}, and each following line is {"record": <JobRecord mapping>}. The hook returns one JSONL response per record, in order: {"job_id": ..., "outputs": {role: value}} or {"job_id": ..., "error": ...}. A response may also carry an "inputs" member, {role: value} with the same wrappers, naming the entries the job consumed (see Inputs); collect_main writes it when the hook returns a Collected with inputs. Each output or input value uses exactly one wrapper:

  • {"entry": {...}} for a registered entry record;

  • {"value": <json>} for a DataRecord;

  • exactly {"file": "<path>"} for a workspace-confined FileRecord.

A declared output ref makes httk-store validation hard-required at collect time. Without a ref, the framework creates a _httk_custom_* property definition.

Response lines are drained as binary newline-delimited data and decoded as UTF-8 one line at a time. Limits are enforced while draining: 1 MiB per response line, 64 KiB per stderr line and 1 MiB of total stderr.

  • A malformed, non-UTF-8, errored, missing, wrong-id or unresolvable response degrades only its own job, and the sweep continues.

  • A limit breach terminates and degrades the affected executable collector group.

  • Surplus blank response lines are ignored; a nonblank surplus response line degrades the whole group.

Python .py hooks run in process with the same assembled-output semantics, and return either a mapping of output roles or a Collected; an ordinary per-job exception degrades that job.

Format fallback and degradation¶

For a job of a compat format (workflow_realization = "language"), provider dispatch is followed by the job’s own workflow_language parameter. A provider-less CWL, PWD or jobflow job then uses the format’s default collector. It reads the output document from the workdir or committed data tree, maps ports to declared roles and creates DataRecord objects. CWL File values must stay inside the workspace, workdir or data tree and are recorded as a file descriptor and sha256. Jobflow reads jobflow-outputs.json.

A package with a custom hook records workflow_collect = "package"; provider-less collection of it degrades with a registration hint instead of running the format default. httk-v1 has no default: such a job degrades with a message to declare [workflow.collect] in a package manifest. The allow_job_collector fallback is tried only after this format fallback, and only with a matching digest.

Any per-job collector, load or assembly failure degrades that job without stopping the sweep; fail_fast=True (--fail-fast) stops at the first such job instead. Interrupts, missing Python dependencies and unavailable definition-validation dependencies still propagate. An executable hook that cannot be launched (for example, from a damaged pinned job tree) degrades its batch, while an unreadable output file degrades only its job. Neither stops other hooks from running.

Batching and streaming¶

collect(..., batch_size=64) consumes records in bounded windows. A matching executable hook runs once per window, and results stay in workspace scan order. fail_fast=True (--fail-fast) forces the window size to one, which disables executable batching and starts one collector process per job. batch_size (--batch-size) must still be positive but is otherwise ignored in that mode.

Normal CLI output is JSONL, streamed as each window completes. --degraded filters the output lines to degraded jobs but keeps whole-sweep summary counts. --into retains the complete sweep so its second storage pass can resolve cross-job provenance; use ordinary streaming collection when that memory cost is too high.

For the distinction between declared entry-typed inputs and opaque implementation parameters, see Workflow packages in detail and Workflow declarations.

Recognized calculations¶

A tree of finished calculations that did not run through a workspace, such as a directory of VASP runs or Quantum ESPRESSO outputs, is collected by walking it:

httk collect calculations/ --dry-run
httk collect calculations/ --into results.sqlite --id-base mydb

Collector packages¶

Each directory is offered to the recognized-calculation collectors: those that code packages register (see Supporting a simulation code) and any given with --collector DIR. A collector is a workflow package with a [workflow.recognize] table, a recognize.py hook, a collect.py hook and no runner. It is collected, never run.

[workflow]
name = "mycode.calculation"
description = "a finished mycode run"

[workflow.recognize]
file = "recognize.py"
priority = 10
requires = ["INPUT", "*.out"]

[workflow.inputs.structure]
role = "initial_structure"
entry_type = "structures"

[workflow.outputs.total_energy]
role = "total_energy"
entry_type = "records"
ref = "https://schemas.httk.org/defs/v0.1/properties/core/total_energy"
product_of = "initial_structure"

[workflow.collect]
file = "collect.py"

# recognize.py
from httk.workflow.calculations import content_digest
from httk.workflow.hookapi import Claim, Unclaimed


def recognize(directory):
    outputs = list(directory.glob("*.out"))
    if len(outputs) > 1:
        return Unclaimed("several outputs")
    return Claim(content_digest(directory, ["INPUT"]))

collect.py is an ordinary collect hook; record.result_file(name) also finds compressed copies such as OUTCAR.gz. Besides declared output roles it may return declared input roles (here the starting structure), which become the run’s input edges.

Recognition¶

requires lists cheap markers: exact basenames or *.ext globs, matched case-insensitively against the directory’s files with any compression suffix stripped. Content lookup is exact: content_digest, record.result_file and existing_file find files by their exact names, and only the compression suffix may vary.

Only a collector whose markers all match has its recognize(directory) hook called. The hook returns:

  • a Claim;

  • Unclaimed when the directory is this code’s but cannot be collected; it is reported with the reason and counted as unclaimed;

  • None when the directory is not this code’s.

A hook that raises declines the directory, except that an ImportError (a missing dependency) stops the sweep. When several collectors claim a directory, the highest priority wins and the others are reported as also matching. A tie at the highest priority is an error unless --prefer NAME (repeatable) names one of them.

Identity¶

The collector chooses the claim’s identity from the calculation’s content, typically content_digest over its input files, so the stored run is <collector name>:<identity> wherever the directory is. content_digest digests decompressed contents, and an absent file differs from an empty one. An in-place rerun with unchanged inputs is the same calculation and stores a revision; changed inputs (cp CONTCAR POSCAR and rerun) make a new calculation.

Duplicates and collisions¶

Within one sweep, two directories claiming the same identity with identical marker files are copies, and the second is skipped. With different marker files they collide, and the sweep stops and names both directories. --exclude PATTERN (a root-relative glob, repeatable) skips one of them.

--dry-run prints how every directory would be claimed, as httk-collect-claim lines, without collecting anything. When collecting, each calculation’s summary or report line carries "directory", its path relative to the swept root, because its job_id is only the identity digest. The walk does not visit directories starting with . or symlinked directories, and it collects a nested workspace as a workspace instead of walking it.

Multi-directory calculations¶

A calculation spread over several directories, such as a phonon calculation whose displacements are separate VASP runs, is claimed in its top directory with Claim(identity, consumes=("disp-001", ...)). Their own collectors still collect the consumed subdirectories. The claiming calculation is collected after them, and its run links to their runs as child runs (has_artifact edges of type runs, labelled by the relative path).

A calculation with a failed part is incomplete. A consumed directory that is missing, excluded or not claimed, or whose own collection degraded, degrades the claiming calculation. The degraded part is still reported on its own line. --dry-run lists the consumed directories on the claiming line.

Python API¶

from httk.workflow import claims, collect_tree, store_collected

for claim in claims("calculations", collectors=["my-collector"]):
    print(claim.directory, claim.kind, claim.collector)

items = list(collect_tree("calculations", collectors=["my-collector"]))
reports = store_collected(items, "results.sqlite", id_base="mydb")

Typed records and store upgrades¶

store_collected stores each calculation’s inputs like its outputs. A DataRecord whose property definition has a typed record kind is stored as that kind, served and filterable under its property name: the core total energy as a TotalEnergyRecord (_httk_total_energy), the average total energy of a molecular-dynamics run as an AverageTotalEnergyRecord (_httk_average_total_energy), the other core kinds such as _httk_temperature, and the analysis kinds such as _httk_bulk_modulus when httk-analyse is installed. Other definitions stay generic records: stored, but their values are not served.

A store’s layout declares every registered record kind, so it depends on the installed packages. When a newer httk or a newly installed package brings another record kind, an existing store is refused with a message naming --upgrade. Rerun with --upgrade (upgrade=True) to append the new kinds. The upgrade is additive: it adds tables and does not rewrite stored rows or ids. Keep a backup of the store first. A store declared with the analysis kinds needs httk-analyse installed to be collected into again.

A store holding generic records of a definition that is now typed (collected before its typed kind existed or before it was used for collected values) is refused, naming those definitions, with advice to rebuild it. Delete it and collect again, keeping the id ledger so record and run ids are preserved.

Ids and re-collection¶

Structures are deduplicated by content and keep the id the store minted for them. Records, runs and files get ledger ids, which a tree sweep signs with the project or operator identity key (tree_ledger_keys).

Re-collecting only adds. A calculation directory deleted since the last sweep stays in the store, and a calculation reverted to the exact content of an older revision writes nothing, so the newer revision stays latest. Rebuild the store in either case.
