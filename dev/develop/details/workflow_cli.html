Project and workflow command line in detail¶

This is the complete command reference, from workspaces and jobs to projects, signed manifests, and remotes. Installing httk-workflow registers lazy workflow, workspace, job, launcher, remote, manager, campaign, config, seal, transfer, v1, and collect commands with httk-core:

httk workflow --help

httk workflow … covers workflow installation and execution; workspace and job management are the top-level trees httk workspace … and httk job …, and collecting results is httk collect. Every group and command answers --help, and a mistyped action is reported by its group. Task-manager usage in detail explains what the commands do to a workspace.

Configuration conventions¶

Concept groups live directly below httk: httk launcher, httk remote, httk manager, httk campaign, httk config, and httk seal. workflow retains workflow installation, inspection, building and execution.

Use show [--json] to inspect configuration and configure to change it. Repeat --set KEY=VALUE to add or replace a value and --unset KEY to remove an override. Supported list settings also offer --add KEY=VALUE and --remove KEY=VALUE; these change individual members, whereas --unset removes the whole override. Workspace, launcher and remote configuration removes overrides before setting new values; user, campaign and daemon configuration applies flags in argument order.

Workspace selection¶

A WORKSPACE, positional or given with --workspace, is a registered name, REMOTE:NAME for a workspace on a remote, or else the path of a local workspace directory (one holding .httk-workspace/, relative to the current directory; no upward search). A registered name wins over a same-named directory, so ./NAME addresses the directory. The registry verbs workspace forget, delete, move and default take registered names only. When the workspace is omitted, commands resolve it in this order: the closest enclosing workspace containing .httk-workspace/format.json, the project’s recorded default, the registry’s default, then an auto-created per-user default.

The registry is machine-owned and stores only absolute local paths, in $XDG_CONFIG_HOME/httk/workspaces.json. When a command reaches a remote workspace, the far side resolves the plain name in its own registry.

Remote-capable commands (workspace status, settings, gc, fsck, job list, show, log, why, request and delete, workflow install, build and run) go through the adapter. Jobs are created locally, moved with job push and brought back with job pull (or job transfer in general).

Creating, moving, and removing workspaces¶

workspace init creates and registers an explicit workspace. The workspace is a directory of its own, never a project root: init refuses a non-empty directory. httk-workflow owns its top level: .httk-workspace/, jobs/ (every job is jobs/<state>/<placement>/<job_key>~p<NNN>~<token>, or flat below jobs/owned/<owner-id>/ while an owner holds it), workflows/, logs/, postprocess/ and, once enabled, exchange/. A canonical path may have only one registered name.

httk workspace init --name my-workspace runs/my-workspace

A workspace on a cluster is addressed as REMOTE:NAME. Its owning machine chooses the path given to workspace init REMOTE:PATH.

workspace move NAME DEST_DIR is an atomic same-filesystem rename and refuses cross-filesystem moves. workspace move and workspace delete refuse while any owner of the workspace is not proven dead: stop its managers first. workspace forget only removes the name. To move across filesystems, stop managers, copy the tree, forget the old name, and re-register it with workspace init --name NAME <newpath>.

Sealing a workspace¶

Sealing is described in full in Sealing jobs, workspaces, and projects. workspace status shows a sealed line (and JSON field). workspace seal records the seal digest of every job, recording and listing jobs without a seal as unsealed; workspace verify reports drift since then. A sealed workspace refuses modifying CLI commands; managers and jobs do not check it.

Application settings and preludes¶

Application settings are a flat map of small dotted values a runner resolves when it runs, such as vasp.command; a value that parses as JSON is stored as that scalar, a bare word as a string. workspace init --setting KEY=VALUE seeds them, and a workspace bound to a remote is also seeded from that remote’s whitelisted settings (a cluster’s vasp_command becomes vasp.command). They are snapshotted into each attempt, so never store credentials there; see application settings.

httk workspace settings set --key vasp.command --value vasp_std \
  --key environment.prelude --value "module load httk" my-workspace
httk workspace workflow-prelude set --workflow relax-vasp --value @prelude.sh my-workspace
httk workspace workflow-prelude show --json my-workspace

environment.prelude applies to every job and workflow-prelude only to the jobs of one workflow id, after it; both run under set -e. A workflow prelude VALUE is stored verbatim, and @FILE reads it from a file. Preludes are workspace-local: a transferred job runs under the destination’s preludes. See environment preludes.

Policy, owners, and checks¶

The workspace policy (visibility_deadline_seconds and the retention.* limits) is stored in format.json; see workspace policy. workspace owners lists who holds jobs, with the liveness the read-only death proof gives from this host. An owner whose death no probe can prove is declared dead by the operator:

httk workspace attest-dead OWNER WORKSPACE --force --reason "node rebooted"

The death proof runs first: an owner proven alive is refused, and one it cannot decide needs --force. Attesting an owner that is still running can apply a request twice and run work twice, so attest only after confirming that the owner process and every launch it started are gone; see owners, death and recovery. workspace fsck must run only while no manager, CLI operation, daemon or transfer uses the workspace; its findings from a busy workspace may be transient, and --repair is refused until every owner is proven dead and recovered by workspace gc. --repair asks for confirmation first; --yes answers it, and is required without a terminal. workspace fsck and workspace gc are described in checking a workspace and freeing disk.

Workflows and builds¶

A job runs only a workflow installed in its workspace. Installed workflows live in workflows/<slug>--<h16>/ and are selected by id, short name (the most recently installed one of that name) or NAME@REF (see Short names).

build: foreground builds of installed workflows¶

httk workflow build [--workspace WORKSPACE] [--json] WORKFLOW...
httk workflow build [--workspace WORKSPACE] [--json] --list

build builds installed workflows (by id, NAME@REF or short name, which selects the newest installation of that name) that declare [workflow.build] for this platform, in the foreground, and registers the artifacts in the installation’s builds/<platform>/; a REMOTE:WS workspace builds on the remote. install already builds for the platform it runs on; run build on each other platform whose managers serve the workspace. --list prints the registered builds. Selecting jobs¶

JOB is a job UUID, a tag--uuid job key, any unique prefix of either, or a path inside the workspace. A job directory names one job; a placement directory names every job below it; and a glob expands to matching entries. Relative paths are resolved from the current working directory and must remain inside the selected workspace. A job’s directory name changes at every move, so scripts should use UUIDs or keys.

Remote job show, job log, job why and job delete accept canonical lowercase job UUIDs only; resolve keys and prefixes locally first.

Creating jobs¶

job new scaffolds and submits jobs of a workflow installed in the workspace. See Quickstart.

httk workflow install --workspace WORKSPACE 'git+https://github.com/httk/workflows-vasp#vasp-relax'
httk job new --workspace WORKSPACE --workflow vasp.relax --input structure=POSCAR --tag silicon
httk job new --workspace WORKSPACE --workflow vasp.relax --input-from structure structures/ --parameter kpoint_density=30.0 --placement project/screening
httk job new --workflow vasp.relax --input structure=POSCAR --parameter publish_data=true
httk job new --from-runner ./my_runner.py --step characterize --parameter sites=8
httk job new --from-command 'my_executable {input}' --file input=input_files/a.dat --tag a

--workflow names an installed workflow by id or short name (the most recently installed one of that name), or as NAME@REF by the tag, branch or commit prefix it was installed from (see Short names). A workflow that is not installed is refused, unless --install installs it first (with its calls): a git URI git+https://HOST/PATH[@REF][#SUBDIR], a package directory (--workflow-dir, installed again when the directory’s sources differ from the installed ones, compared by the installed digest’s rules), or a workflow name known on this machine. A runner file, command template or bare workflow document is always installed ad hoc, as adhoc:<name>@<digest>. The job records the installed workflow’s id, pinned to the full commit for a git workflow.

A runner supplied with --from-runner is run in describe mode to infer its workflow and initial step, so it must call httk_workflow_runner WORKFLOW STEP... before any work.

Other options:

  • --embed-workflow embeds the workflow in the job’s <job>/workflow/ instead of naming an installation (see Workflow packages in detail, Embedded workflows). It works with --workflow, --workflow-dir, --from-runner and --from-command, installs nothing, and is refused together with --install. The job’s workflow id is embedded:<name>@<sha12>. Language realizations, [workflow.build] packages and uninstalled fixed callees are refused, and the tree must hold no symlink, special file, hard-linked file or __pycache__.

  • --parameter NAME=VALUE supplies an implementation parameter; VALUE is JSON when it parses as JSON, and NAME=@FILE reads a JSON file. For example, the workflows-vasp workflows keep their results in the persistent workdir run/ and copy a curated set into data/ only with --parameter publish_data=true.

  • --environment NAME=VALUE overrides one declared workflow environment entry.

  • --call ALIAS=WORKFLOW binds the workflow’s call slot ALIAS to WORKFLOW (a workflow name or commit-pinned git URI, like a [workflow.calls] reference (never a path), installed first with --install, which also installs an unbound slot’s default) instead of its default; --call-parameter ALIAS NAME=VALUE gives the bound workflow one parameter, spelled as for --parameter. Both repeat. See call slots.

  • --format FORMAT selects the format of a bare document (see Running workflow documents).

  • --priority (0 is highest) and --step override the workflow’s defaults.

  • --duplicate-tag {refuse,skip,allow} decides what happens when a job with the same --tag already exists in the same placement (exactly that placement, not its subtree) in any state, away and running included. The default refuse fails with a job with tag 'TAG' already exists in placement 'PLACEMENT': KEY (STATE); pass --duplicate-tag allow to create another or --duplicate-tag skip to skip it (the API raises httk.workflow.DuplicateTagError with tag, placement and existing). skip leaves the existing job, warns skipped tag TAG: already KEY (STATE) and goes on; a batch ends with submitted N jobs (K skipped), and new_job(..., duplicate_tag="skip") returns None. allow creates another. Jobs without a tag are never checked, job submit and spawned children are unaffected, and deleting a job frees its tag. The check precedes the creation, so two creators racing on one tag can both succeed; workspace fsck notes jobs sharing a tag in one placement (a noted finding duplicate_tag, not a failure). Re-running a creation script with skip thus creates only the jobs that do not exist yet, wherever the existing ones are, as httk v1’s fixed task directories did.

The command prints one tab-separated job_key<TAB>directory line per job, or a report with --json. The directory is where the job sits now; it changes as the job moves between states.

Inputs, files, and batches¶

  • --input NAME=PATH stages one declared input.

  • --input-move-from-job NAME=PATH moves (renames, never copies) PATH into the declared input NAME’s destination. PATH must be a regular file (not a symlink) inside the payload of a succeeded job of the same workspace, not job.json, state.json, workflow/ or anything below attempts/, logs/ or .httk-job/, and on the workspace’s filesystem; anything else is refused. A sealed job keeps its seal: a signed release record amends it (see Sealing jobs, workspaces, and projects), and the file’s staged_files digest is the one the seal records, so the file is never hashed. An unsealed job’s file is hashed, with a warning. If the job is not created, the file moves back. Repeatable; not for the same NAME as --input, and not with --input-from.

  • --input-from NAME SOURCE... loads a file or the readable files in a directory and creates one job per file for a batch. A directory file with no registered reader whose name follows a structure convention (POSCAR*, *.vasp) is read as POSCAR; any remaining unreadable files are skipped and named on one stderr line.

  • --file NAME=PATH stages anything else; a NAME without / lands in files/.

  • --files DIR stages every regular file directly inside DIR under its own name. Subdirectories and other non-file entries are skipped with one stderr warning.

job.json lists the --file/--files files, and the declared inputs’ destinations, under staged_files with the size and SHA-256 of each as staged, and collect records each --file/--files file as a files input of the job’s run, labelled by its payload-relative path (see Collecting results).

After a batch, one final stderr line reports submitted N jobs. If a batch fails partway, it instead reports submitted N of M jobs before failing and exits 2. In a batch, --tag becomes a prefix combined with each item’s derived tag (run7-si2o); for a single job, --tag is the whole tag.

Command templates¶

With --from-command TEMPLATE, shlex-style words are turned into a one-step Bash runner, installed ad hoc as adhoc:command@<digest>. The template is an argv-only word list with no shell syntax. Each {name} placeholder must have a matching --parameter NAME=VALUE or --file NAME=PATH. Parameter placeholders resolve through httk_workflow_parameter at run time; file placeholders resolve to the absolute path of the file’s copy in the job workdir ($PWD/<basename>, since the command runs there), never to the staged payload file, so the command cannot rewrite the input collect records. {{ and }} emit literal braces.

Each --file input is copied into the job workdir under its basename before the command runs; two inputs with the same basename are refused at job new, as is a --file staged below the workdir run/. Existing workdir entries are never replaced, so a retry keeps working on the copy an earlier attempt left. The generated runner can be edited and passed back with --from-runner.

Running workflow documents¶

Run a PWD, CWL, or jobflow document directly with job new --from-runner DOCUMENT; the document is installed ad hoc and run by the manager’s built-in realization:

httk job new --workspace WS --from-runner flow.cwl --input message=echo
httk job new --workspace WS --from-runner workflow.json --parameter pwd_module_path='["."]'
httk job new --workspace WS --from-runner maker.json

--format accepts cwl, pwd, jobflow, and httk-v1 for bare document inputs. See Compatibility with other workflow systems.

Requests¶

job request ACTION [JOB_ID...] posts one request per job and requires --reason. Jobs are the JOB_ID selectors joined with every job in a --state STATE (repeatable, an unowned state); --step STEP (repeatable) narrows both and alone selects from every unowned state, and --placement PREFIX narrows --state, or a --step without JOB_ID, to a placement subtree. --state, --step and --placement select in a local workspace only, and a selection with no job exits 1 with no jobs selected. The actions are cancel, pause, continue, restart, override_step (with --override-step STEP), set_priority (with --priority), set_budget (with at least one of --max-attempts-per-activation N|unlimited, --max-total-attempts N|unlimited and --max-activations N|unlimited; the options are valid only with set_budget), set_workflow (with --workflow WORKFLOW: an installed id, short name or NAME@REF, resolved once in the jobs’ workspace, on the remote side for a remote one; every job is checked against it before anything is posted, and a workspace daemon remote refuses it), detach, unlock, eject (with --destination), delete, seal and unseal. An away job accepts no request but delete (see Away copies below). The CLI applies each at once to a job no owner holds; a job held by an owner gets it once, at that owner’s next boundary. What each action does is tabulated in the task-manager guide. --force accepts reviving a child a parent’s observations name (continue, restart, override_step) and publishes an override_step outside the runner’s recorded steps. restart refuses, posting nothing and exiting non-zero, a job that recorded a failed or cancelled child its rerun spawning step would reuse: it prints an error: line per such child and the remedy (continue --tree, or httk job delete the child); --force restarts anyway. The revival guard does not apply to a child that its parent’s join still names (the parent failed at its wait, or waits on it again). A revival (continue, restart, override_step) restores the job’s declared retry allowance; --keep-budget (only with those actions) keeps the current limits instead. --tree (only with continue, also over ssh, not for a workspace daemon remote) also resumes the failed descendants of the job reachable through retained joins, deepest first, before the job itself, forwarding --keep-budget to each; see Restarting and resuming jobs.

After publication, the CLI immediately serves the pending requests of each unowned job, from a snapshot taken then, oldest first by created_at instant and request id, up to and including the published one. Each request prints its job id, request id, outcome (applied, queued, refused or uncertain) and an explanation. A job held by another owner, or one needing a manager’s reconciliation, keeps its request queued for that owner or manager, and so does a job with more than 256 pending requests; when an earlier request of the job cannot be served, the published one reports the same outcome and reason. Exit status is 0 for applied or queued requests and 1 for a refusal or uncertain result. --wait is valid only for pause; it waits for queued pauses and exits 0 only when each reaches paused. A superseded, dropped or timed-out pause exits 1. --timeout SECONDS requires --wait.

job delete, job seal, job unseal, job detach and job unlock use the same immediate serving path and print one concise line per job: done, or the queued, refused or uncertain outcome with its explanation.

For an ordinary remote workspace, job request ACTION --workspace REMOTE:NAME JOB_ID ... keeps the signed two-leg request-envelope exchange: the client signs the request documents with the identity selected by --operator, then sends them back for verbatim publication. With continue --tree the far side expands the selection to the failed descendants, deepest first; the client signs only continue requests, each requested job among them, notes each added job on stderr, and has the far side post and serve them one at a time, stopping at the first that does not resume. The far side also applies the restart refusal before anything is signed. A mounted-daemon remote instead sends one signed typed command for each selector. Daemon batches are non-atomic: earlier commands may have been accepted if a later command fails. A mounted daemon executes a command only for an exchange root submitted with the signing key; other targets are refused with not_owner. The daemon accepts canonical job UUIDs and UUID prefixes; glob and tag selectors are refused before publication. Daemon --force is unsupported.

Use --request-id with exactly one daemon-mediated job command to retry the same command after an uncertain transport result. An exact retry must retain the selector, action, reason, options and configuration pin. It reuses the original command ID and cached signature; changing any command field is rejected. The option is not available for local jobs or ordinary remote workspaces.

For pause --wait, the client sends the pause command once and then polls with fresh signed observations until the daemon reports paused, refusal, terminal supersession or timeout. Passive status.json is not evidence that a command completed. Run httk remote daemon status REMOTE --request-id ID to inspect a previously sent daemon job command; each inspection uses a fresh signed observation request. Without --handle or --request-id, status remains passive and informational.

Inspecting and debugging jobs¶

job list, job show, job log, and job why read one workspace without writing anything, and job debug drives a single job to a terminal state in the foreground. See Task-manager usage in detail for what each reports.

httk job list --workspace WORKSPACE --state ready
httk job show --workspace WORKSPACE JOB
httk job log --workspace WORKSPACE --limit 20 JOB
httk job why --workspace WORKSPACE JOB
httk job debug --workspace WORKSPACE --follow-children PAYLOAD_OR_JOB

job debug exits 0 on success, 3 on failure, and 4 when the job stopped without finishing.

job list --json returns format, format_version, jobs, and next_after. Each row has job_key, job_id, state, step, phase, placement, priority, token and owner_id. step is the step the job is at: its current activation’s, or the initial step of its job.json before the first activation (earlier releases reported null there). To page a large workspace, use --limit N and pass the returned next_after (<state>:<cursor>) to --after; it is null when the listing is exhausted. Paging is weakly consistent: a job that moves between pages can appear twice or be missed, so deduplicate by job_id. --counts adds per-state totals, which need a full directory walk and ignore --step.

--state STATE and --step STEP select jobs in the same way across job list, job transfer, job request, collect, campaign collect and postprocess: each repeats (the values of one option are alternatives), and a job must match every option given. A job whose step cannot be determined (an unreadable job.json or a damaged state.json) matches no --step: job list logs a warning, job request leaves it out with a note, job transfer reports an error, and collect counts it as unreadable. --step reads each examined job’s job.json and state.json, so like --tag-contains a sparse --step page with --limit may examine up to max(100 × limit, 10000) jobs (two small reads each) and come back partial, with a next_after that resumes the scan. This selector --step is not the --step of job new and job debug, which names the step a job starts at; job request override_step names the step a job resumes at with --override-step.

job why also lists held jobs: a job held for a transfer is in neither state tree, and job why JOB shows its hold, destination and the way back.

Sealing, detaching and unlocking jobs¶

job seal and job unseal are the per-job half of Sealing jobs, workspaces, and projects. job seal seals a succeeded job that has no seal yet, with the workspace’s seal.keys. job unseal releases a succeeded job from its seal, after confirmation, which is what lets job delete remove it.

job detach permanently makes a spawned job independent of its parent: it no longer moves with its parent’s tree, it can be transferred on its own, and Attempt.parent reads None for it. It stays in any join that references it. A job with no parent is refused.

job unlock [--no-copy] [--reason TEXT] JOB... puts jobs in debug mode (see Restarting and resuming jobs). It posts an unlock request per selected job and, marker-only and nearest first, per ancestor of each (by the parent recorded in job.json, also for a detached job), and applies them at once to unowned jobs. Ancestor lines end with (ancestor); an ancestor already unlocked prints already unlocked (ancestor) and is not an error, and a parent that cannot be found prints <job_id> parent <key> not found; not unlocked without changing the exit status. It exits 1 when a request of a selected job or ancestor is refused or uncertain. job request unlock does the same on a local workspace, ancestors included, with the same lines and exit rules. Without --no-copy it copies the job’s installed package/ to workflow/ in the job directory (a reserved payload name), where the manager then runs the runner from, while the job is unlocked, and the operator edits it. The marker cannot be cleared by any request. A succeeded job with a live seal is refused until job unseal, and a cancelled job is refused. job unlock refuses a remote workspace as job detach does; job request unlock reaches an ssh remote through the signed request envelope (it copies; a spawned job is refused there: unlock spawned jobs on the workspace host with httk job unlock, which also unlocks their ancestors), and a workspace daemon refuses it (the daemon does not carry unlock; run it on the daemon host). job show prints an unlocked row, job why a “debug mode” check, and the JSON report gains unlocked and paths.runner_copy (<payload>/workflow); workflow_pin.source (installed or copy) appears in the JSON report too. The jobs are collected only with httk collect --force.

Ejecting and adopting jobs¶

job eject and job adopt move jobs out of a workspace and into one without either workspace knowing the other. Reach an unregistered workspace with httk -C DIR or --workspace.

httk job eject JOB /scratch/out
httk job eject --tree --wait JOB /scratch/out
httk job adopt --workspace other /scratch/out/JOB_KEY

job eject takes one root in any unowned state and moves it into DEST/<job key>: a plain directory holding bundle.json and the complete job directories under jobs/<placement>/<job key>/, with seals inside the payloads. DEST is an absolute directory, or a missing name in one. A root whose descendants are present is refused unless --tree is given; with --tree every descendant must be terminal or paused, and they travel in the same bundle. --wait first posts pause requests and waits (up to --timeout, default 600 s) until the jobs can move, so a running job leaves paused. job eject records the selected identity’s public key as the optional, unsigned owner_key in bundle.json; --operator IDENTITY selects that identity and eject fails without moving the job if it has no key. Without --operator, the configured default identity is used when keyed, and the member is omitted when not. --hold and --operator cannot be combined. Only untrusted (exchange) adoption uses owner_key. Across filesystems the bundle is copied to a hidden partial name in DEST and renamed into place when complete. The command prints ejected N job(s) to PATH. A failed delivery returns every job to the state it left.

--hold puts the bundle in the workspace’s own .httk-workspace/transfers/outgoing/<transfer id>/ instead, the first leg of job transfer; DEST, when given, and --destination-id are then only recorded.

job adopt BUNDLE... validates each bundle and publishes each job into the state and priority it left, printing JOB_KEY<TAB>STATE<TAB>DIRECTORY per job and a warning naming workflows that are not installed here. Several bundles are adopted in turn by one command; a refused one does not stop the rest, and the command exits 0 only when every bundle was adopted or already was. --json prints one document, {"bundles": [...]}, with an entry per BUNDLE in argument order: bundle (as given) and status (adopted, already_adopted, refused, taken or failed, the last for an error that is no refusal of the bundle, such as a full disk), plus already_adopted, published and missing_workflows for an adopted bundle, or a message for the others. On one filesystem it takes the bundle by rename. Across filesystems it copies the bundle and leaves the source in place, unless --move is given, which removes the source after a successful publication (the way to fetch an exchange return). A bundle whose jobs are all present already reports already adopted; one with only some of them present, or whose root’s parent is present here, is refused. Bundle structure is checked strictly: no symlink or special file in protocol positions, every member’s job.json agreeing with the manifest, and an adopted job’s placement satisfying the placement rule.

job adopt --stdin-tar (no BUNDLE) is the receiving end of a push: it reads the bundles as one tar stream on standard input, extracts it whole into a fresh landing transfers/incoming/<token>/ with the same filters as a pull (a malformed stream or a refused member exits 2 and adopts nothing), then adopts every top-level bundle directory in it and removes the emptied landing. A bundle whose bundle.json records another destination workspace id is refused and discarded there. The --json document then also carries workspace_id, this workspace’s id, and, for each hidden --built-for ID, a workflows entry {"id", "status", "tree_sha256"} with status present, unbuilt or missing.

Both commands are crash-safe and take no file locks: each records what it needs to finish before it moves anything, so an interrupted eject or adoption is rolled forward or back once the killed command’s death is proven and its scratch recovered, by a manager tick or by workspace gc on its host. Delivery is at least once: verify the destination before ejecting or adopting a copy again by hand. Neither works in a sealed workspace or project; a sealed job keeps its seal.

Moving jobs between workspaces¶

job transfer moves jobs between two workspaces, each a registered name (REMOTE:WS for a workspace on a remote) or else a workspace directory; a registered name wins over a same-named directory, so ./NAME addresses the directory. Any combination of local and remote ends works, and a remote-to-remote transfer is relayed through the client:

httk job push [SRC] DST [--no-keep] [--job JOB … | --state STATE … | --step STEP …] [--placement PREFIX] [--no-workflows] [--json] [-q]
httk job pull SRC [DST] [--job JOB … | --state STATE … | --step STEP …] [--placement PREFIX] [--no-workflows] [--json] [-q]
httk job transfer (--job JOB … | --state STATE … | --step STEP …) [--placement PREFIX] [--tree] [--keep] [--no-workflows] SRC DST [--json] [-q]
httk job transfer --resume [--keep] [SRC] [DST]
httk job transfer --release TRANSFER_ID [--release TRANSFER_ID …] [--keep [--destination-id ID]] [WS]
httk job recover [--workspace WS] (JOB … | --all [--placement PREFIX])
httk transfer status [WS] [--json]

job push and job pull are the everyday forms: job push REMOTE:WS moves every ready job (created, waiting to start) of the workspace the command runs in, else the default workspace, to REMOTE:WS, and job pull REMOTE:WS moves every succeeded job of REMOTE:WS back. With one positional push takes it as DST and pull as SRC; the omitted end resolves like any omitted workspace (the enclosing workspace, the project’s default, else the per-user default, which is created on first use), and with none the command is refused. Both always act as --tree, and --job, --state or --step replaces their implicit state (--step without --state selects from every unowned state except away; --state away is refused by push, pull and transfer). --resume, --release, --hold and --destination-id stay on job transfer.

Jobs are selected by name with --job (a UUID, key, unique prefix, path or glob), or by state with --state STATE, which takes every job of SRC in that state (any state of job list --state except owned), optionally only under a placement prefix with --placement PREFIX. Both repeat and combine; a job selected twice moves once. --step STEP (repeatable) narrows --job and --state to jobs at that step; alone it selects from every state but owned (and --placement then narrows it as it narrows --state), and a --job at another step is left out with a note on stderr. httk job transfer --state succeeded sigma:runs default brings every finished job home in one command. A tree is never split: --state and --step leave out every job whose (not detached) parent is in SRC, so a child moves only inside its root’s bundle, and a note on stderr counts the children that did not move that way. Without --tree, a selected job whose descendants are present is refused, so a campaign whose finished roots have children is fetched with --state succeeded --tree; a root’s tree then carries all of its descendants, which must be terminal or paused (a failed, cancelled or paused child travels with a succeeded root). A root whose children are not all terminal or paused (a parent that an any_terminal, any_succeeded or at_least join let finish first) is refused and stays, never split. A child that should move alone is detached first. A very large selection on a remote SRC is held in one call: give it time with --adapter-timeout. Should that call fail, the jobs it held are still driven by the same run or by --resume.

A transfer is four steps. It holds each selected job on SRC (with --tree, its terminal or paused descendants too) in SRC’s own .httk-workspace/transfers/outgoing/<transfer id>/, recording DST, after which the jobs are in neither workspace’s state trees. It copies the held bundle to DST (on one filesystem adoption simply moves it in; a local DST receives it with the adapter’s pull; a remote DST receives it with the adapter’s deliver, streamed into job adopt --stdin-tar there), adopts it there into the states and priorities it left, and only then releases the hold. A remote end is never probed first: its commands name the workspace by the plain name it has on the far side. On a remote SRC, --job needs canonical job UUIDs; --state and --step are resolved there.

The workflows the held jobs need (each job’s effective workflow and the closure of its calls, as SRC resolves them) that DST lacks and SRC has are installed in DST under the same ids, and a shipped workflow with [workflow.build] is built there, as is a needed one DST already had without a build for its platform. For a local DST this happens before the first adoption of a batch, from DST’s store; the builds follow the release. A remote DST reports what it has with the adoption itself (job adopt --built-for ID, each present, unbuilt or missing), and only when something is missing or unbuilt one more remote start follows: one deliver of the store entries (install.json and package/) to the internal workflow install --stdin-tar --build [--also-build ID …], or, with nothing to install, one workflow install --also-build ID …. Adopting before installing is safe: a manager skips, and does not fail, a ready job whose workflow is not installed yet. An installation DST already has is never replaced, even with another tree. --no-workflows skips all of this. With --json each outcome lists workflows, one {id, status} per needed workflow: installed, present, mismatch (DST keeps its other tree, which the jobs run), missing (installed in neither), refused or failed (with a reason), or unbuilt (installed, its build failed; the reason names the httk workflow build remedy). Adoption warns about jobs whose workflows DST still lacks. The command prints one line per hold, TRANSFER_ID<TAB>STATUS<TAB>N job(s)<TAB>DESTINATION, and exits 0 only when every hold was adopted or already was. Progress, one line per step, goes to stderr unless -q/--quiet is given.

Each hold is its own bundle, but the holds bound for one destination travel as one batch, so the number of adapter calls, ssh connections and remote httk starts does not grow with the number of jobs: one hold call on a remote SRC (its answer also lists the other holds already bound for DST, so no transfer status call follows), one pull of every bundle from a remote SRC, one deliver to a remote DST (which lands the bundles in .httk-workspace/transfers/incoming/<batch token>/ and adopts them in the same start), and one release call on a remote SRC. Local to remote takes one ssh connection and one remote httk start; remote to local three connections (hold, pull, release) and two starts; remote to remote four connections and three starts. Shipping missing or unbuilt workflows to a remote DST adds one connection and one start. A delivery is one call for the whole batch (its bundles travel in the stream); only a hold, pull or release whose id list exceeds 64 KiB of command text (some 1500 jobs) is split, into as many such calls as it needs.

A bundle DST refuses (for example because some of its jobs are already there, or because its bundle.json records another destination workspace id) stays held on SRC and is reported; one whose jobs are all at DST already is “already adopted”, and its hold is released. When a remote DST refuses a delivery before adopting anything (the workspace name is unknown there, the stream was refused), a local SRC takes those holds back at once and reports them not_moved with DST’s reason; a remote SRC keeps them held (failed). An answer that cannot be read (a banner on the connection, a crash, a timeout) marks every hold of that call failed and leaves it held: whether the jobs arrived is unknown, and --resume delivers again (they then report “already adopted”) and releases. Releasing such a hold by hand instead, after checking with httk job show that DST has the jobs, keeps away copies only with httk job transfer --release T --keep --destination-id ID SRC, where ID is the workspace_id that httk workspace status --json REMOTE:WS reports for DST.

Recovery. Delivery is at least once. Every run, and job transfer --resume, first re-drives the holds of SRC bound for DST (--resume without DST re-drives every hold to the destination it records), so a transfer interrupted at any step is finished by running it again. A pushed hold records the destination locator only (no probe runs before a push); DST’s workspace id is learnt from the adoption and recorded in the away copies. A hold that does record an id (a local DST, or --destination-id) is adopted only by that workspace: the far side refuses a bundle that records another workspace’s id. Accepted limitation: if a push’s answer was unreadable and the remote workspace NAME is then pointed at another workspace before --resume, the resume delivers to the new workspace and the jobs exist in both; after such a change, check with httk job show or httk job list on the remote before resuming. transfer status lists the holds of a workspace (transfer id, root job, member count, destination, age), job why JOB explains a held job, and httk project repair --dry-run reports holds and incoming copies older than seven days. A transfer abandoned for good is taken back into SRC with httk job adopt --workspace SRC SRC/.httk-workspace/transfers/outgoing/<transfer id>, which is safe only after checking that DST does not have the jobs; job transfer --release T discards a hold whose jobs DST has (add --keep --destination-id ID to keep away copies, as above). job transfer --hold (--job JOB … | --state STATE … | --step STEP …) SRC DST only holds jobs in a local SRC, recording DST as given; it is the first leg a client runs on a remote SRC. With --json it prints {"holds": [...], "held_before": [...], "errors": [...]}, where held_before lists, in the same shape, the other holds of SRC already bound for the same DST locator. --release T --keep --destination-id ID keeps away copies that record ID as their destination workspace when the hold recorded none (a push learns that id from the adoption report).

Away copies¶

job push leaves in SRC an away copy of every job it moves (--no-keep opts out), and job transfer --keep does the same; a plain job transfer moves. An away copy is a job in the seventh unowned state, away (jobs/away/<placement>/…). It never runs, is not collected and cannot be transferred or requested; only job delete works on it. Its state.json records away: the destination workspace id and locator, the transfer id, the state and priority the job left, and the time. After a keeping push the command prints kept N away copies in SRC (httk job list --state away; httk job recover JOB to resend), and --json outcomes carry "kept": true|false. httk job list --state away lists what you are still waiting for, and job why and job show explain an away job.

job pull (or any trusted transfer back) replaces the away copy when the job returns from the workspace it was pushed to. A bundle from another workspace is refused: KEY is away at X, but this bundle comes from workspace Y; recover or delete the copy first. An interrupted transfer finished with --resume is released with the --keep of the run that releases it (a push re-drives with keeping unless --no-keep).

job recover (JOB … | --all [--placement PREFIX]) [--workspace WS] returns an away tree, its root and the spawned descendants, to the states and priorities it left, so that a job lost at its destination can be pushed again. A job that is not a root is refused with a message naming its root. It prints recovered KEY: N job(s) back to STATE; refusals print KEY: <message> on stderr and exit 1. It works on local workspaces only. Nothing checks whether the job still runs at its destination: recovering one that does and pushing it elsewhere runs it twice. A late return of the old remote job is refused afterwards: nothing is overwritten and the hold stays on the remote, so delete one of the two, or adopt the bundle in another workspace. Away copies are not kept through the workspace daemon’s exchange.

Remotes¶

Named after git remote, a remote is one machine this project can reach, together with the bundle of adapter operations that reaches it. REMOTE:NAME names a workspace on a remote. The name local is reserved for the built-in remote meaning “this machine”, so remote add local is refused.

Remote definitions and templates¶

Remote definitions are versioned directories containing remote.json and one executable adapter; project definitions shadow global ones. Writing a remote adapter in detail is the reference for writing your own: the bundle layout, the request and result documents of the six operations (configure, install, invoke, push, pull, and status), and the optional daemon operation. The module packages four maintained templates for remote add --template:

  • local: same-machine transport;

  • ssh: one tar stream per transfer plus command execution over SSH;

  • mount: a locally mounted remote filesystem plus a command executor;

  • mount-daemon: files as the only channel, through a mounted exchange directory, plus typed requests to a confined broker.

The first three use the target workspace’s manager.launch setting. mount-daemon refuses generic REMOTE:NAME operations; move jobs with job eject into the exchange inbox and job adopt --move out of its outbox. See Remotes for configuration and request-ID retry rules.

Remote settings¶

remote configure --set KEY=VALUE persists only the machine-level keys check_connectivity, check_mount, cli_prelude, exec_command, exchange, host, httk_command, interactive_auth, legacy_settings, mount_root, port, remote_root, username, vasp_command, and vasp_pseudo_library in the shareable remote.json. Scheduler profile values are workspace settings (slurm.*, manager.workers) and are refused as remote settings. Other keys are stored in the remote’s credentials.json beside it, with mode 0600; project manifests exclude that file.

remote import-v1 maps legacy httk v1 computer bundles by reading assignment-only configuration; legacy shell executables are never run, and legacy SLURM_* values belong in a slurm launcher instead.

local copies files in this filesystem and runs child processes; ssh moves files as one tar stream over a single ssh connection per push or pull and runs commands on the configured host; mount copies through a locally mounted view and runs commands through exec_command. httk_command overrides how httk is spelled on the far side. Every subprocess an adapter starts is an argument vector, quoted element-wise where ssh needs a far-side shell.

httk on the target: remote check¶

httk is never installed on a remote for you. The requirement is that the adapter’s non-interactive shell can run httk, with httk-workflow installed beside the core. Run remote check once after configuring a new remote: it confirms that the host answers, that httk is found (also trying python3 -m httk.core.cli), and that the workflow command group exists. If the check fails, set up httk₂ on the remote reachable from a non-interactive shell, use the remote’s cli_prelude setting, or point httk_command at it.

Projects¶

The project anchor and every project verb (init, show, import-v1, export, repair, adopt, manifest create | verify, seal, unseal, and verify-seal) belong to httk-core. httk-workflow registers the workspace as a project-member kind, so core’s verbs delegate a workspace’s internals to it: what to leave out of a manifest, how to seal it, its seal digest, how to verify it, and its health checks.

A workspace inside a project is recorded in httk_project/members.json: registered on httk workspace init, unregistered on workspace delete or workspace forget, and its path followed on workspace move. On another machine, httk workspace adopt (per workspace) or httk project adopt (every member) registers copied workspaces under their recorded names.

httk project repair handles conditions that quietly break a project later: dead owners not yet recovered, scratch of unknown owners, old temporaries, holds and incoming copies older than seven days, a workspace missing from the registry, and a member not yet adopted on this machine. It repairs only through gc and adoption. --dry-run only reports, and --no-adopt skips adopting.

To seal a project, run httk workspace seal and then httk project seal. Verify the whole tree with httk project verify-seal or httk seal verify.

Signed manifests and operator identity¶

Signed manifests¶

httk project manifest create .
httk project manifest verify
httk project manifest verify --trusted-key keys/collaborator.pub

The httk₂ manifest is deterministic canonical JSON lines compressed with bzip2. It records sorted POSIX paths, regular-file sizes and SHA-256 hashes, empty directories, and symlink targets; special files are rejected. A domain-separated body digest is signed with Ed25519. A member workspace is left out of the project manifest: it is covered through the workspace seal chain instead.

What a verified manifest proves¶

The signing key lives in the tree it signs: httk_project/keys/project.seed has mode 0600 and is excluded from the manifest, but not absent. Anybody who can write the project directory can re-sign it. A manifest proves that the tree is exactly what somebody with the seed described; it is not a tamper seal against an attacker with write access. Verification compares the signing key with a trust anchor that did not come from the manifest: the key pinned in project.json at httk project init, plus any key named with --trusted-key.

Verdict

Exit

Meaning

valid_trusted

0

the manifest describes this tree and a pinned key signed it

valid_unknown_key

3

the manifest describes this tree, but nothing here pins the key that signed it

invalid

1

the tree does not match the manifest, the signature does not verify, or the manifest names another project

A project made before key pinning existed verifies as valid_unknown_key until a key is adopted explicitly with httk.workflow.projects.pin_project_key or trust_project_key.

Operator identity¶

Operator identity (the recorded name, email, default, and named identities) lives in $XDG_CONFIG_HOME/httk/identity.json, managed by httk-core. httk init creates the first named identity and its key pair and makes it the default; httk identity add --name NAME --email EMAIL SHORT adds more, and httk identity default SHORT changes the default.

job request records the selected identity’s Name <email> label and signs the request with that identity’s key. Omitting --operator selects the default identity. A selector containing < is a literal Name <email> label, signed with the default identity’s key; any other selector must be a configured short name. For remote requests the control-center identity signs locally. If a configured identity’s key file is missing or unreadable, the request fails loudly.

Signatures are detached, cover the canonical JSON of the whole document, and are domain-separated from every other httk signature. They are optional: a request without one is applied, but one whose signature does not verify is malformed and quarantined by gc. A signature means attribution, not authorization: anyone who can write the workspace’s request directory can still post an unsigned request. Job control through the workspace daemon is the exception: the daemon accepts only commands signed by a key in its own authorized_keys policy (see Confined workspace daemon).

Protocol spellings and removed commands¶

One machine runs these argument vectors on another over an adapter. They are protocol, not operator interface, and hidden from --help where they are not ordinary commands; their spelling is frozen because the far side may run a different httk. The batched job transfer --hold, the repeated --release, job adopt --stdin-tar and workflow install --stdin-tar need both ends to run the same httk-workflow release. An older SRC answers the hold with an error and no hold document, so nothing is held. An older DST rejects --stdin-tar: the holds are reported failed and stay held, and with any answer the client does not recognise the jobs may have arrived. Upgrade DST, check with httk job show whether the jobs are there, and then release the hold with httk job transfer --release (or re-run --resume after the upgrade):

httk job transfer --hold --json [--tree] [--destination-id ID] [--job JOB …] [--state STATE …] [--step STEP …] [--placement PREFIX] -- WS DST
httk job transfer --release TRANSFER_ID [--release TRANSFER_ID …] [--keep [--destination-id ID]] WS
httk job adopt --json --stdin-tar --token TOKEN --workspace WS [--built-for ID …]   (bundles as tar on stdin, by deliver)
httk workflow install --json --workspace WS [--also-build ID …] --stdin-tar --source-label TEXT --build   (store entries as tar on stdin, by deliver)
httk workflow install --json --workspace WS --also-build ID …
httk transfer status --json WS
httk job request-envelopes ACTION --workspace WS --operator LABEL --reason TEXT [--priority N] [--override-step S] [--workflow W] [--destination D] [--max-attempts-per-activation N|unlimited] [--max-total-attempts N|unlimited] [--max-activations N|unlimited] [--force] [--keep-budget] [--tree] JOB_ID …
httk job publish-requests --workspace WS --document JSON [--document JSON …] [--wait] [--timeout S] [--sequential]
httk workspace status --by-path --json PATH
httk workflow manager run --by-path --workspace PATH

The hidden --by-path switch makes the workspace argument a literal path with no registry lookup, so one machine can address another machine’s workspace. The hidden job delete --confirmed is the remote half of a confirmed delete.
